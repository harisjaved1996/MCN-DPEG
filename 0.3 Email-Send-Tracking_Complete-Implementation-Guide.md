# Email Send Tracking — Complete Implementation Guide
### Every send creates a CRM record on the Investment with live per-contact statuses (Sent / Opened / Clicked / Bounced), synced back from Marketing Cloud Next / Data Cloud

This is the full build guide for the tracking layer that sits on top of the One-Button Investment Email system (guides 0.1 / 0.2). It was built, broken, fixed, and verified in the real org (`plaid`) — including one discovery that invalidated the first design and forced a rework. Everything below reflects the final, working system.

**What existed before:** the Send Email buttons trigger a bulk MCN send, but CRM records nothing — no history of what was sent, to whom, or whether anyone opened it.

**What exists after:** every Execute click creates an **Email Send** record under the Investment (subject + metrics: total / sent / opened / not opened / clicked / bounced / open rate) with one **Email Send Recipient** child per contact carrying that contact's individual status — and those children also appear on the **Contact page** as an "Investment Emails" related list, giving a permanent per-contact email history.

---

## 1. What the client experiences

1. Click **Send Email with LWC** on any Investment → pick email → review investors → Execute (unchanged).
2. Instantly, an **Email Send** record appears under the Investment: "Distribution - Plaza - 2026-07-16 01:09", status *Broadcast Requested*, every selected contact listed as a *Pending* recipient.
3. Within ~15 minutes (or immediately via the **Refresh Metrics** button), statuses flow in from Data Cloud: recipients flip to **Sent**, the real email **subject** fills in, counts update.
4. As investors open and click, recipients advance to **Opened** / **Clicked** (with timestamps, open/click counts, last-clicked URL); bounces surface as **Bounced** with the reason.
5. Open any Contact → **Investment Emails** related list → every email that contact was ever sent, with status. Open any Investment → **Email Sends** related list → every campaign fired at its investors.

**Status semantics (say it to the client):** a recipient's status is the *highest* engagement reached: `Pending → Sent → Opened → Clicked`, with `Bounced` overriding everything. *Opened* = the tracking pixel loaded (image-dependent; some mail apps block or prefetch images). *Clicked* = a link/button in the email was actually clicked — the reliable signal, and a click also proves an open even when the pixel was blocked. A recipient that stays *Pending* forever was suppressed by MCN (opted-out) — "selected but never confirmed sent" is correct, visible behavior.

## 2. The architecture at a glance

```
[Send Email with LWC button] → InvestmentEmailController.sendEmail
        ├─ insert Send_Exclusion__c rows          (existing, unchanged)
        ├─ insert Email_Send__c + Email_Send_Recipient__c rows   ★ NEW
        │   (recipients = resolved investors − deselected; all Pending;
        │    same fail-closed transaction — DML failure ⇒ no email goes out)
        └─ enqueue BroadcastCalloutJob(..., emailSendId)
                └─ POST → Investment_Broadcast_Flow → MCN bulk send
                └─ markBroadcastOutcome → status Broadcast Requested / Failed

[MCN sends] → engagement events land in Data Cloud: ssot__EmailEngagement__dlm

[EmailSendMetricsSync]  (scheduled :00/:15/:30/:45  +  Refresh Metrics button)
        └─ InvestmentEmailTracking.syncOpenSends()
             ├─ CLAIM: each Pending recipient claims its flow-run GUID   ★ the clever part
             ├─ APPLY: pull all events of the claimed runs → per-contact status
             └─ ROLLUP: recalc master counts (recalcMetrics pattern)
```

**Division of labor:** the send pipeline writes the *intent* (who was selected) instantly; Data Cloud is the source of truth for *outcomes*; a sync job reconciles the two. Nothing blocks the user — tracking rows are two fast DMLs, and all DMO querying happens async.

## 3. ⭐ Read this first: the discovery that shaped the design

**One broadcast Execute produces a DISTINCT flow-run GUID PER RECIPIENT.** Every engagement event carries `ssot__FlowElementRunId__c` = `<GUID>#<SendElementName>` (e.g. `0cebae11-…#Send_Distribution_Email`). The first build assumed one GUID per Execute click — and in live testing, one recipient synced while the other silently stayed Pending, because MCN had stamped each recipient's events with a *different* GUID at the *same millisecond*.

**Consequence: correlation must be per-recipient.** Each `Email_Send_Recipient__c` claims *its own* GUID (stored in `Flow_Run_Id__c` on the recipient). All of that recipient's later opens/clicks/bounces carry the same GUID, so once claimed, metrics can never bleed between sends — even for a contact who belongs to two investments emailed the same minute.

## 4. Out-of-the-box analysis (what MCN gives you for free — all verified in-org)

MCN stores everything, but in **Data Cloud**, not CRM objects. There is NO OOTB per-contact/per-investment related list — hence this module. The raw materials:

| Fact | Detail |
|---|---|
| `ssot__EmailEngagement__dlm` | One row per event. **Directly SOQL-queryable from Apex** via `Database.queryWithBinds(soql, binds, AccessLevel.SYSTEM_MODE)`. (SYSTEM_MODE is rejected in *anonymous* Apex only — deployed classes are fine.) |
| `ssot__IndividualId__c` | **Is the CRM Contact Id** (003…) — identity resolution keyed on it. Direct join, no fuzzy matching. |
| `ssot__EngagementChannelActionId__c` | `SEND_STATUS` (with `ssot__EmailRecipientSendStatus__c = 'SENT'`), `OPEN`, `CLICK`, `MESSAGE_PROCESSING_TIME` (pipeline telemetry — **ignore**). |
| `ssot__FlowElementRunId__c` | `<GUID>#<SendElementName>` — **one GUID per recipient per broadcast** (see §3). |
| `ssot__BulkEmailMessageId__c` | Points to a standard **`ListEmail`** record whose `Subject` is the real sent subject (query it OOTB). `HtmlBody`/`TextBody` are always **null** — content lives in MCN CMS, which is why this module shows subject only. |
| Bounce/click fields | `ssot__EmailBounceType__c`, `ssot__BounceReasonText__c`, `ssot__LinkURL__c`. |
| Timing | Engagement rows lag the send by **~5–15 minutes** (Data Cloud ingestion). Design for retry, never for immediacy. |

# PART A — Data model

## A1. `Email_Send__c` (label "Email Send") — one per Execute click

Object: Text name field, ReadWrite sharing, reports/search on, View override → flexipage `Email_Send_Record_Page`. Repo: `force-app/main/default/objects/Email_Send__c/`.

| Field | Type | Purpose |
|---|---|---|
| `Investment__c` | Lookup(Investment__c), required, Restrict, rel. `Email_Sends` | the Investment related list |
| `Email_Choice__c` | Picklist (restricted): Distribution, CapitalCall | which email |
| `Send_Run_Id__c` | Text(36), ext. id | our UUID — joins to `Send_Exclusion__c` rows of the run |
| `Flow_Run_Id__c` | Text(255), ext. id | *representative* claimed GUID (first recipient's) — audit |
| `List_Email_Id__c` | Text(18) | the ListEmail id from engagement |
| `Subject__c` | Text(255) | real subject, auto-filled from `ListEmail.Subject` at claim |
| `Status__c` | Picklist: Queued, Broadcast Requested, Broadcast Failed, Syncing, Completed, No Engagement Data | lifecycle |
| `Sent_At__c`, `Last_Synced_At__c` | DateTime | Execute time · last sync |
| `Total_Recipients__c`, `Sent_Count__c`, `Opened_Count__c`, `Clicked_Count__c`, `Bounced_Count__c` | Number(18,0) def. 0 | recalculated in Apex |
| `Not_Opened_Count__c` | Formula: `Sent_Count__c - Opened_Count__c` | |
| `Open_Rate__c` | Formula(Percent): `IF(Sent_Count__c > 0, Opened_Count__c / Sent_Count__c, 0)` | |
| `Error_Message__c` | LongTextArea(4000) | callout failure body |

**Lifecycle:** `Queued` (created) → `Broadcast Requested` (callout 200) or `Broadcast Failed` (non-200 / exception — but see the self-heal note in §B4) → `Syncing` (≥1 recipient claimed) → `Completed` (7 days after send; drops out of the scheduled scan — Refresh Metrics still works). `No Engagement Data` = nothing claimable 24 h after send.

## A2. `Email_Send_Recipient__c` (label "Email Send Recipient") — one per selected contact

ControlledByParent. Repo: `force-app/main/default/objects/Email_Send_Recipient__c/`.

| Field | Type | Purpose |
|---|---|---|
| `Email_Send__c` | **MasterDetail**, rel. `Recipients` | |
| `Contact__c` | Lookup(Contact), rel. `Investment_Email_Receipts`, label **"Investment Emails"** | ⭐ the Contact related list |
| `Email__c` | Email | address snapshot at send time |
| `Flow_Run_Id__c` | Text(255), ext. id | ⭐ THIS recipient's claimed GUID (per-recipient — §3) |
| `Status__c` | Picklist: Pending, Sent, Opened, Clicked, Bounced | highest engagement reached |
| `Sent_At__c`, `Opened_At__c`, `Clicked_At__c`, `Bounced_At__c` | DateTime | first occurrences |
| `Open_Count__c`, `Click_Count__c` | Number(9,0) def. 0 | |
| `Last_Click_URL__c` | Text(255); `Bounce_Type__c` Text(80); `Bounce_Reason__c` Text(255) | detail |

## A3. `Investment_Email_Option__mdt` (Custom Metadata Type)

One record per email option; **DeveloperName = the choice value**; field `Flow_Element_Name__c` Text(80) = the Send Email Message element API name in the Broadcast Flow. Records shipped: `Distribution` → `Send_Distribution_Email`, `CapitalCall` → `Send_CapitalCall_Email`. The claim algorithm matches engagement rows by this element name. Repo: `objects/Investment_Email_Option__mdt/` + `customMetadata/`.

# PART B — The Apex (repo: `force-app/main/default/classes/`)

Five classes. Design principles, each earned:
- **Fail closed:** tracking rows are inserted *before* the callout is queued, in the same transaction as exclusions — a DML failure means no email goes out untracked.
- **Gateway seam:** all DMO access goes through `InvestmentEmailTracking.EngagementGateway` (an interface with a swappable `static gateway` instance). Production = dynamic SOQL (`DlmGateway`); tests inject a fake — DMO rows cannot be inserted in test context, and dynamic SOQL means no compile-time dependency on Data Cloud schema.
- **Recompute-from-scratch idempotency:** every sync rebuilds each recipient's state from ALL events of its run and diffs against the stored row — same events in, same fields out, only changed rows updated.

## B1. `InvestmentEmailModels` — the `EngagementRow` DTO
One DMO event, decoupled from schema: `flowRunId, contactId, action, engagedAt, sendStatus, linkUrl, bounceType, bounceReason, bulkEmailMessageId`.

## B2. `InvestmentEmailTracking` — the engine

**`createSendRecord(investmentId, investmentName, emailChoice, sendRunId, recipients)`** — inserts the master (Status Queued, Sent_At now, Total = size) + one Pending recipient per contact. Two DMLs.

**`markBroadcastOutcome(emailSendId, success, detail)`** — called by the queueable after its callout (DML-after-callout is legal): 200 → *Broadcast Requested*; anything else → *Broadcast Failed* + `Error_Message__c`.

**The claim algorithm** (`claimRecipientRuns`, per send, oldest-first across the batch):
1. Element name for the send's choice from the CMDT (fallback: `Send_<Choice>_Email`).
2. Fetch `SEND_STATUS` rows for the *unclaimed* recipients' contact ids in window `[Sent_At − 5 min, Sent_At + 24 h]`.
3. Keep rows whose `flowRunId` ends with `#<elementName>`; group per contact.
4. Exclude `(flowRunId | contactId)` pairs already claimed by **another send's recipient** (SOQL on `Email_Send_Recipient__c.Flow_Run_Id__c`) or earlier in this same cycle — this is what keeps back-to-back sends of the same email from stealing each other's events, because the older send is processed first and claims the earlier rows.
5. Each recipient claims the **earliest remaining** row of its contact → `Flow_Run_Id__c`.
6. First claim decorates the master: representative `Flow_Run_Id__c`, `List_Email_Id__c`, and `Subject__c` from `ListEmail.Subject`.
7. Nothing claimable → retry next cycle (ingestion lag); still nothing 24 h later → `No Engagement Data`.

**Engagement application** (`applyEngagement`): one query — all events `WHERE ssot__FlowElementRunId__c IN :recipientRunIds` — then per contact, **strictly scoped to the run that recipient claimed**:
- `SEND_STATUS` + `SENT` → Sent_At (min), floor *Sent*
- `OPEN` → Opened_At (min), Open_Count, floor *Opened*
- `CLICK` → Clicked_At (min), Click_Count, Last_Click_URL (latest); a click with no OPEN also sets Opened_At (blocked images); floor *Clicked*
- any row with non-null `bounceType` → *Bounced* (overrides), Bounce_Type/Reason
- `MESSAGE_PROCESSING_TIME` / unknown contacts → ignored

**`recalcMetrics(Set<Id>)`** — rollup identical in shape to `SignatureRequestTracking.recalcMetrics`: Total = children; Sent = status ∈ {Sent, Opened, Clicked}; Opened/Clicked from timestamps; Bounced from status.

**Entry points:** `syncOpenSends()` (batch: 10 sends per cycle, oldest first, statuses Queued / Broadcast Requested / **Broadcast Failed** / Syncing — failed is scanned on purpose, see B4) and `syncSend(id)` (Refresh Metrics — works on any status, returns a user-facing message).

## B3. `EmailSendMetricsSync` — the clock

⚠️ **A class cannot implement both `Schedulable` and `Queueable`** ("Queueable cannot be implemented with other system interfaces") — hence: outer class `implements Schedulable` whose only job is `System.enqueueJob(new SyncJob())`; inner `SyncJob implements Queueable, Database.AllowsCallouts` runs `syncOpenSends()` and chains once if more remain. Keeping DMO SOQL out of the scheduled context also preserves a REST-API fallback (the gateway seam makes that a one-class change).

Scheduling (Apex cron has no `*/15`) — run once in Execute Anonymous:
```apex
System.schedule('EmailSendMetricsSync :00', '0 0 * * * ?', new EmailSendMetricsSync());
System.schedule('EmailSendMetricsSync :15', '0 15 * * * ?', new EmailSendMetricsSync());
System.schedule('EmailSendMetricsSync :30', '0 30 * * * ?', new EmailSendMetricsSync());
System.schedule('EmailSendMetricsSync :45', '0 45 * * * ?', new EmailSendMetricsSync());
```

## B4. Changes to the existing pipeline

**`InvestmentEmailController`** (the LWC path — the ONLY path that creates tracking, by design decision):
- `getInvestors` now delegates to a shared `resolveInvestors(recordId)` — `sendEmail` re-resolves investors **server-side** (recipients = resolved − deselected), so tracking can't be spoofed by a stale client list.
- `sendEmail`: exclusions → `createSendRecord` → enqueue the queueable with the new 4th argument `emailSendId`. All inside the existing fail-closed try.
- New `@AuraEnabled refreshEmailSend(Id)` → `syncSend` (backs the Refresh Metrics button).

**`InvestmentEmailSender`**: `BroadcastCalloutJob` gains a 4-arg constructor (`emailSendId`); the 3-arg one delegates with null, so **the screen-flow path is untouched and untracked** (per decision — make the LWC button the go-forward one). After the callout it calls `markBroadcastOutcome`. **Timeout self-heal:** a timed-out trigger may still have executed (0.1's known ambiguity) — the sync deliberately scans *Broadcast Failed* sends too, and a successful claim is the proof the send actually happened; the record then advances to *Syncing* on its own.

# OPERATIONS

**New email option — the ritual grows to 4 touches:** 1) Content: create + Publish the email. 2) Broadcast Flow: add the Decision outcome + Send element → re-Activate — **note the Send element's API name**. 3) Button lists: add the choice (flow radio and/or LWC option). 4) ⭐ **NEW: add an `Investment_Email_Option__mdt` record** — DeveloperName = the choice value, `Flow_Element_Name__c` = the Send element API name — *and add the value to the `Email_Choice__c` picklist*. Miss touch 4 → sends work but claims fall back to the `Send_<Choice>_Email` naming convention; if the element was named differently, tracking shows *No Engagement Data*.

**Where results live:** the Email Send record is the client-facing view. The DMO remains the raw source of truth. Exclusion rows remain the audit of deliberate skips; `Send_Run_Id__c` joins the two.

**Which button:** only **Send Email with LWC** creates tracking. The screen-flow button still sends (unchanged) but records nothing — retire it or tell the client.

# TROUBLESHOOTING (every one actually happened)

| Symptom | Cause | Fix |
|---|---|---|
| One recipient synced, others stuck *Pending* forever (first build) | Assumed one FlowElementRunId per broadcast — MCN stamps **one GUID per recipient** | Per-recipient claiming (`Flow_Run_Id__c` on the recipient) — §3. If you rebuild from scratch, start there |
| `System.SecurityException: Cannot use SYSTEM_MODE access level in anonymous execution` | Anon-Apex-only restriction | Probe with USER_MODE in anon; deployed classes keep SYSTEM_MODE |
| `Queueable cannot be implemented with other system interfaces` | One class implementing Schedulable + Queueable | Outer Schedulable + inner `SyncJob` Queueable |
| Flexipage: `missing required property [parentFieldApiName]` / "parent record name is invalid" | `force:relatedListSingleContainer` metadata quirks | Use `force:relatedListContainer` (the Master Document page's component) |
| Second deploy: "Could not find entity" for objects the first deploy "created" | A failed deploy **rolls back everything** — componentSuccesses in a failed deploy are pre-rollback noise | Redeploy the full set together |
| Contact related list not visible | Org has 4 Contact layouts; admin uses `SDO - Contact`, not "Contact Layout" | Find the real one via Tooling `ProfileLayout`, edit that |
| Send stuck *Queued*, engagement exists in DMO | Sync not scheduled, or claim window passed | Check `CronTrigger` for the 4 jobs; Refresh Metrics works regardless of schedule |
| *Broadcast Failed* but investors got the email | Trigger callout timed out after MCN accepted it | By design the sync scans failed sends — a successful claim self-heals it to *Syncing*. Never manually retry the send |
| Opened count looks high/low | Pixel-based opens (prefetching/blocking) | Trust clicks; help text on `Opened_Count__c` says so |
| Metrics 0 right after sending | Ingestion lag (~5–15 min) | Wait; Refresh Metrics; the claim retries every cycle for 24 h |

# KNOWN LIMITATIONS (accepted trade-offs)

1. **Subject only, no body** on the master — `ListEmail.HtmlBody` is null (content lives in MCN CMS). Fetching via the CMS API is a future enhancement.
2. **LWC path only** creates tracking (user decision). The flow button is legacy.
3. **Statuses lag by up to the sync interval** (15 min) plus ingestion lag — Refresh Metrics for on-demand.
4. **Suppressed (opted-out) recipients stay *Pending*** — correct but worth explaining to the client.
5. The `ssot__IndividualId__c` = Contact Id join depends on the current identity-resolution config; changing the ruleset key would break claiming.
6. Bounce mapping is defensive (keys off non-null `bounceType`) — no live bounce had occurred yet to confirm the action id.
